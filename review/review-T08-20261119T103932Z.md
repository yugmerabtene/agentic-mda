## Vérifications spécifiques

- **Format CVE** : les 28 identifiants respectent `CVE-YYYY-NNNN` et correspondent à des CVE réelles référencées par le NVD.
- **Source** : toutes les entrées ont `source: "nvd"` et une `source_url` pointant vers `nvd.nist.gov`.
- **Périmètre** : le script refuse les cibles publiques (`test_dry_run_public_target_refused`, code != 0, aucun appel réseau). L'IP `192.168.56.103` est RFC1918 et autorisée par `scripts/recon/scope.py`.
- **Déduplication** : les CVE sont uniques par `id` (pas de doublons dans `cves.json`).
- **Faux positifs signalés** : 4 entrées dans `false_positives` (CVE-2007-4752, CVE-2010-4755, CVE-2004-0925, CVE-2003-1070), correctement justifiées (version hors plage, OS incompatible).
- **Faux positifs non détectés** : au moins 7 CVE Apache (F-002) + CVE-2024-27305 (F-003) échappent à la détection.

## Risques résiduels et limites

- La corrélation repose sur une recherche par mot-clé NVD (`keywordSearch`) sans CPE exact dans la requête API ; certaines correspondances sont approximatives (confiance "medium" au plus). Une validation par CPE (`cpeName`) réduirait les faux positifs.
- Le cache NVD (TTL 24 h) peut renvoyer des données obsolètes si le NVD met à jour une fiche entre-temps.
- Aucun CVE n'est marqué KEV (`kev: false` partout) ; la priorisation par exploitation connue n'est pas disponible sans clé API NVD / CISA KEV.
- Les tests unitaires mockent le réseau ; aucun test d'intégration contre le NVD réel n'est automatisé (l'exécution réelle a été faite manuellement via le cache).

## Décision

`CHANGES_REQUIRED` : le dev doit corriger la logique d'exclusion de versions (`_version_excluded`), relancer la corrélation pour éliminer/reclasser les faux positifs non signalés (F-001, F-002, F-003), appliquer `ruff format` (F-004), puis le reviewer re-contrôlera. Aucun blocage d'accès ou d'information n'empêche la correction.
